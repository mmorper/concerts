**Status:** Planned
**Target Version:** v7.0.0
**Priority:** High
**Estimated Complexity:** Very High
**Dependencies:** None blocking. Related: #89 (video pilot), #159/#164 (dashboard + alert webhook), #252 (image revocation), #315 (dead venue photos)

---

## Executive Summary

The archive publishes liner notes to `/liner-notes`, an RSS feed, and per-post OG cards. Nothing carries them any further. This spec adds outbound syndication to social platforms, and a second content stream — **On This Day** — that fills the gaps between weekly liner notes.

The shape is **POSSE** (Publish on your Own Site, Syndicate Elsewhere): the site stays canonical, and every social post is a deliberately lossy pointer back to it. The goal is clicks to the archive, published under a dedicated `morperhaus concerts` identity, fully automatic once running.

Two things make this larger than "call some REST endpoints." First, **the creative work gates the engineering work** — what a post looks like on each channel determines what fields the payload needs, so a mock phase runs before any schema is frozen. Second, **the archive owns none of its current imagery** — every image source in `image-refs.ts` is licensed for display on this site, not for republication under a brand account. Both are resolved in Phase 0 before a single post goes out.

## Design Philosophy

The site is canonical and the social post is a pointer. That framing decides most arguments before they start: when a post could either tell the whole story or make someone want the story, it makes them want it.

Two rules follow, and both are load-bearing:

**Authored, never derived.** A social payload is written on purpose, in the archive's voice, by the same generation step that writes the note — not chopped out of the first paragraph. Every RSS-to-social bridge in existence fails here, and it is the single most visible tell that an account is automated.

**Permanent facts only, harder than before.** `.claude/skills/liner-notes-voice/SKILL.md` already forbids perishable claims because posts are permalinked and RSS-syndicated. Syndication tightens that ratchet: a note deleted from the site leaves its social copies standing on servers we don't control. The mitigation is not caution, it is a **retraction path built in Phase 1**, not retrofitted.

## Phase 0 — Creative Investigation

**This phase ships no production code.** It exists to produce decisions that later phases depend on. It is the largest phase in the spec and the one most likely to be skipped under pressure. Do not skip it.

### Why it must come first

The payload's text fields *are* creative decisions:

- If the winning Instagram format is a single card, the payload needs `hook: string`
- If carousels win, it needs `beats: string[]` — 3–5 discrete narrative units, each with its own length budget

These are different schemas. The second is not reachable from the first without breaking every adapter and regenerating every post already syndicated. Same for hook length: "about 180 characters" stops being a design note the moment it becomes a field the generator writes against and `voice-check.ts` validates.

Mock first, learn the content shape, *then* freeze the schema.

### Mock corpus (real data only — no lorem)

Mocks are built from actual archive records, chosen to include the ugly cases. Designs die on edge cases, and all of these exist in the real data:

| Case | Why it's in the corpus |
|---|---|
| A median liner note | The baseline everything is judged against |
| Longest artist name in `artists-metadata.json` | Type overflow in headline position |
| Longest venue name in `venues-metadata.json` | Type overflow in footer/metadata position |
| A `full-circle` post (two artists, two dates) | Densest data payload any detector produces |
| An On This Day date with 4 shows | `06-04`, `11-16`, `06-10` each have four. Tests the multi-record layout |
| A post whose image ref resolves to nothing | The `PLACEHOLDER_IMAGE_URL` branch, which #252 made reachable |
| A 40-year anniversary record | The best-case On This Day post, for the high end |

### Imagery tracks

Text-only is a hypothesis, not a conclusion, and it is not assumed here. There is no personal photo or ticket-stub archive to draw on, so the investigation mocks four tracks and picks — possibly a hybrid, possibly different answers per channel:

**Track A — Typographic / editorial.** Design-system ground, hook set large, date and venue as footer, wordmark. The existing solid-color fallback path in `og-image.ts`, promoted to a primary treatment. Risk to test: austerity. A feed of type-on-color can read as corporate rather than personal.

**Track B — Data-derived generative.** The site *is* data visualization — D3, a sunburst, a force graph, timelines, a genre palette. A post about 34 years of one artist can carry a generated constellation or timeline built from the archive's own records. This imagery is **wholly owned, unique to this archive, impossible to mistake for stock, and already on-brand.** Consult `.claude/skills/dataviz/` for palette and form discipline. This track is the most promising answer to "text-only isn't viable" and is available to almost no other project.

**Track C — Material / metaphor.** The project's own metaphor is album liner notes. Mock record-sleeve inserts, gatefold stock, vinyl, and *designed* ticket-stub pastiche — original artwork evoking the object, not a scan of one. Owned, distinctive, and thematically exact.

**Track D — Licensed third-party photography.** Cover Art Archive covers (most defensible: album art adjacent to commentary about that album), and Wikimedia CC-licensed concert photography (attribution required, which on Instagram means in-caption). Mocked so the option is evaluated on merit rather than eliminated by nervousness — but gated on the provenance policy below.

### Image provenance policy (Phase 0 deliverable)

`image-refs.ts` resolves post imagery from three third-party sources. Every one of them is licensed for display **on this site**, not for republication as post imagery under a brand account:

| Source | Used for | Problem when republished |
|---|---|---|
| Google Places photos | Venues | Places terms scope display to Google's service with attribution; caching is limited. Separately, #315 reports 65 of 67 currently dead (403). |
| Spotify album art | Artists (top tracks) | Spotify's design guidelines prohibit modifying or overlaying their content — exactly what the dark overlay + headline does. |
| Cover Art Archive | Albums | Most permissive of the three, but CAA does not warrant rights; underlying covers are label copyright. |

Compositing these into an OG card on our own domain, adjacent to the article discussing them, is a defensible contextual use. Publishing the same composite as native imagery on a branded account makes us the publisher rather than the linker.

The realistic risk is not litigation — it is an automated content-ID or DMCA strike, and a new account with no goodwill cannot absorb one. Losing a handle registered across five platforms to a strike in week three is the specific failure this policy prevents.

**Deliverable:** a written policy stating, per source, whether it may be used for syndicated imagery, under what attribution, and on which channels. Enforced in code in Phase 1.

### Rendering technology decision

Decide this *during* Phase 0, not after.

`og-image.ts` composites hand-built SVG through sharp. That works well for the current card. If the mocks land on real typography — text wrapping, font fallback for names with diacritics, multi-panel layouts — hand-built SVG will fight back, because line breaking becomes our problem.

If mocks are built in HTML/CSS and then reimplemented in hand-rolled SVG, fidelity is lost in translation. **Satori** renders JSX/HTML→SVG and would let the mock and the production renderer share an idiom; the v3 spec named it as a candidate before the current compositing work landed.

Choose the mock medium so that **the mock is a prototype, not a picture of one.**

### Surfaces to mock beyond the single post

Two surfaces that get skipped and shouldn't:

**The profile grid.** Instagram shows nine posts together and the grid is its own design surface. If every card is one template with different text, the grid reads as a bot — visible only by mocking nine at once, never by perfecting one. Same idea for a Bluesky/Mastodon timeline: what does a *scroll* look like. This is the most common way archive accounts end up looking automated despite good individual cards.

**The cross-channel sheet.** One post rendered for every channel, side by side. Whether they read as one brand is invisible until they are adjacent.

Also: **render a contact sheet at true feed scale.** Cards get judged at 100% zoom and then live at ~140px in a feed. A generated sheet at real display size catches more problems than any amount of eyeballing full-size PNGs.

### Comparator study

Before drawing anything, assemble a reference set — music-archive accounts, museum "on this day" accounts, the ones that do this genuinely well. Not to copy, but because a mock phase needs a quality bar that isn't "better than a blank card."

### Vehicle

Use the **design canvas** (`/design`). Multiple artboards on one pan-and-zoom surface means every channel format and media track sits side by side and gets compared as a set. Direct pixel-pushing beats round-tripping edits through a model for creative iteration.

Artboards: each channel × each media track, plus the nine-up Instagram grid, plus a timeline scroll, plus the worst-case corpus, plus the cross-channel sheet.

### Phase 0 exit criteria

Phase 0 is complete when all of the following are **decided and written down**:

- [ ] Per-channel MVP media format — dimensions, what lives in-image vs. in-caption
- [ ] Text budgets per format, expressed as concrete character counts
- [ ] Which payload fields those budgets imply (`hook` vs. `beats`, and how many)
- [ ] Visual language: inherits the site's design system, or gets its own
- [ ] Imagery track(s) chosen per channel, from A/B/C/D or a hybrid
- [ ] Image provenance policy, written, per source, per channel
- [ ] Rendering technology: hand-built SVG, satori, or Playwright screenshot
- [ ] Which media ladder levels are worth building at all — "carousels win, video doesn't" is a legitimate and valuable finding
- [ ] On This Day card architecture (date-forward, not headline-forward)
- [ ] Nine-up grid does not read as robotic

## The Two Ladders

Channels and media are **independent axes**. Channel rollout must not block on media sophistication, and vice versa.

### Media ladder

| Level | Content | Notes |
|---|---|---|
| **L0** | MVP renders per Phase 0 decision: 1200×630 (link cards) + 1080×1350 4:5 (Instagram) | Reuses the existing sharp/SVG path. Auto-generated alt text everywhere. |
| **L1** | Per-platform tuning — safe areas, per-aspect hook lengths, the On This Day variant | Instagram needs shorter lines than the OG card |
| **L2** | Instagram carousels — 3–5 panel narrative | Graph API supports up to 10 images; one extra call over single-image |
| **L3** | Photography and video | Licensed imagery per the provenance policy; #89's video output |

### Channel ladder

| Tier | Channel | Auth reality | Link handling |
|---|---|---|---|
| 1 | **Bluesky** | App password, no expiry, no review | Clean link cards |
| 1 | **Mastodon** | Single token, no expiry | Clean, no penalty |
| 2 | **Instagram** | Professional account + Meta app, 60-day token refresh | No clickable captions — link-in-bio |
| 2 | **X** | OAuth2 refresh, terms churn | Deranked; link goes in first self-reply |

**Explicitly out of scope:** Reddit (the API is free and easy, which is the trap — automated self-promotion violates site-wide rules and subreddit norms; post by hand or not at all), LinkedIn (audience mismatch), Pinterest (wrong image shape, app review).

## Canonical Payload

> ⚠️ **PROVISIONAL — depends on Phase 0.** The shape below is the current best guess and exists to convey intent. Its text fields must be revised against Phase 0 outputs before implementation. See §"Why it must come first".

One canonical payload, N dumb adapters. Adapters **truncate and format only** — they never make content decisions. That keeps voice consistent without auditing N prompt variants, makes a new channel a formatting function rather than a content pipeline, and means one voice-check failure blocks syndication everywhere by construction.

```ts
interface SyndicationPayload {
  slug: string
  kind: "liner-note" | "on-this-day"
  hook: string              // PROVISIONAL — may become beats: string[]
  url: string               // permalink, per-channel UTM applied by adapter
  media: MediaAsset[]       // see media contract below
  tags: string[]
  eligible: boolean         // false blocks syndication entirely
}

interface MediaAsset {
  role: "card" | "panel" | "video"
  aspect: "1.91:1" | "4:5" | "1:1" | "9:16"
  path: string
  alt: string               // required, never optional
}
```

**Put the media contract in the payload, not the adapters.** Each adapter takes what it can use. Then L2 and L3 add new media kinds without touching a single adapter. If media lives in adapter code, every ladder step becomes an N-platform edit.

**Leave the video slot in from day one.** #89 has sat at its go/no-go since April, partly because a rendered video has nowhere to go. A `role: "video"` asset means the pilot plugs into Reels/Shorts at L3 without rework, and reframes #100's open-ended question into the answerable "does video earn its slot."

## Ledger, Idempotency and Retraction

**Ledger:** a committed `syndication-log.json`, keyed by `slug × platform`, storing the returned post URI and timestamp. Never post if the pair exists. Committed rather than KV because it is diffable, reviewable, and greppable — which is how this project already treats every other piece of state.

**Partial fan-out:** Bluesky succeeds, X 500s. Because state is per-pair, a retry resumes only what failed. Retrying the batch would double-post to Bluesky.

**Retraction is Phase 1, not later.** Fully automatic and no-way-to-undo are different decisions, and only the first was chosen. Because the ledger stores returned post IDs, a `retract <slug>` path can delete across all channels — which buys back everything a human approval gate would have, with no weekly clicking. This is cheap now and *impossible to retrofit* if the IDs were never recorded.

**Seed the ledger before the first run.** ~55 liner notes are already published. An empty ledger means the first run fires all of them.

**Backlog drip.** Rather than merely suppressing the back catalogue, run a deliberate rate-limited backfill: one archived note per week alongside the new one. Doubles content volume for a year at zero marginal cost, and means a new account isn't empty on day three. Must be an explicit mode, never an accident.

**Stagger the fan-out.** Minutes of jitter between channels. Simultaneous posting reads as botlike.

## On This Day

### Supply reality (measured, not estimated)

Computed from `public/data/concerts.json`:

| Metric | Value |
|---|---|
| Total concerts | 184 |
| Distinct calendar days covered | **145 of 366 (39.6%)** |
| Days with exactly 1 show | 117 |
| Days with 2+ shows | 28 |
| Busiest days | `06-04`, `11-16`, `06-10` (4 each) |
| Shows hitting a round 5/10/15/20+ year anniversary in 2026 | 25 |

### Cadence

**Post only on days that hit.** ~145 posts/year, averaging 2.8/week, irregular but always genuine. Do **not** widen the window to "this week in" to manufacture a daily cadence — the moment the window stretches to fill empty days, every post weakens and the account becomes a content mill. Irregular-but-real is the correct trade for an archive.

### Anniversary weighting

Not all hits deserve a post. Score them and let weak ones simply not publish — there are 145 slots and only ~100 need filling:

- **Round anniversaries** (5/10/15/20/25/30/35/40 years) score highest — 25 available in 2026
- **First time seeing an artist** now seen many times
- **First show at a venue** that became a regular
- A one-off show from 7 years ago scores lowest and should usually not publish

### Cross-linking

When an On This Day hit lands on a show an existing liner note already covers, link **the liner note**, not the generic deep link. This recycles evergreen content into fresh impressions — which is most of how small accounts actually accumulate clicks — and makes the two streams feed each other rather than compete.

Build all URLs with `src/utils/deepLinks.ts` and assert against `test/fixtures/deep-link-urls.json`. Never hand-build them.

## Platform Notes

**Bluesky.** Rich-text facets must be computed manually using **byte** offsets, not character offsets — a common source of mangled links. Link cards need the thumbnail uploaded as a blob first; Bluesky will not scrape our OG tag. Set the account handle to `concerts.morperhaus.org` via DNS TXT — free, self-verifying, and it puts the URL in front of every reader of every post.

**Mastodon.** Supports an `Idempotency-Key` header — a free second layer of double-post protection on top of the ledger. Add `rel="me"` on the site for profile verification.

**Instagram.** Captions carry no clickable links; the bio link is the path. Point it at `/liner-notes` rather than the homepage — newest-first means the top post is always the one the caption refers to. Aspect ratio must fall between 1.91:1 and 4:5; 4:5 outperforms square. Carousels (L2) are the strongest format and map naturally onto a liner note's structure.

**X.** Post carries the story, first self-reply carries the link — sidesteps the derank. Build this into the adapter from the start; retrofitting it into an adapter shaped around single posts is more expensive. Free-tier terms have changed repeatedly; **verify current limits before implementing** rather than trusting this document.

## Operations

**Silent token death is the defining failure mode of an unattended system.** Instagram's 60-day refresh and X's rotating tokens will both eventually fail quietly, and nobody notices for a month. Surface a "last successful post per channel" timestamp on the operator dashboard (#159) and route failures through the alert webhook slot already sitting unwired in #164.

**Analytics.** Distinct UTM parameters per channel from day one. In three months this answers which channels actually deliver, rather than inviting a guess. The likely finding is that one channel produces most clicks and two produce nearly none — and the correct response is to cut the dead ones. Channel count is a maintenance cost, not an asset. Follow `.claude/skills/analytics/SKILL.md` for event naming.

**Where it runs.** GitHub Actions, as a stage after the existing pipeline — the pipeline already runs there, secrets already live there, and logs, retries and manual re-runs come free. A Cloudflare Worker cron only wins if syndication should be decoupled from the build, which it shouldn't. Do **not** self-host a scheduler (Postiz/Mixpost/n8n); adding a server and database to a static site + Workers stack to call a few HTTP endpoints weekly is a bad trade.

Secrets follow `docs/SECRETS.md`.
